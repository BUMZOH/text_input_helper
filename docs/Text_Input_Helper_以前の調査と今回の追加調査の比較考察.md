# Text Input Helper

## 以前の調査資料と今回の追加調査の比較・考察

## 1. はじめに

Text Input Helperでは、グローバルホットキー

``` text
Ctrl + Shift + Space
```

を使ってTkinterの入力画面を表示している。

以前にも、ホットキーがときどき反応しなくなる問題が発生し、
原因調査を行った。

以前の調査では、当初使用していた

``` python
keyboard.add_hotkey()
```

による組み合わせ判定をやめ、

``` python
keyboard.on_press()
keyboard.is_pressed()
```

を組み合わせて、自分でホットキー成立を判定する方式へ変更した。

その時点では動作が改善したため、その方式で実運用しながら
様子を見ることにしていた。

しかし、その後の実運用で再びホットキーが反応しなくなる現象が発生した。

そこで今回、さらに詳しい切り分け調査を行った。

本資料では、

-   以前の調査で分かっていたこと
-   今回新しく確認できたこと
-   2つの調査結果に矛盾があるか
-   現時点でどこまで原因を絞り込めているか
-   技術資料をどのように残すべきか

を整理する。

# 2. 以前の調査で発生していた現象

以前のプログラムでは、グローバルホットキーを次のように登録していた。

``` python
keyboard.add_hotkey(HOTKEY, show_window)
```

例えば、

``` python
HOTKEY = "ctrl+shift+space"
```

として、

``` text
Ctrl + Shift + Space
```

が成立したときに、

``` python

```

を呼び出す構成だった。

しかし実際に使用していると、

``` text
Ctrl + Shift + Spaceを押す
        ↓
何も起きない
```

という現象が発生した。

# 3. 以前の調査で確認したこと

以前の調査では、キー入力そのものを取得できているか確認するために、
個々のキーイベントをログへ出力した。

その結果、不具合発生時でも個々のキー入力は取得できていた。

一方、

``` python

```

``` text
        ↓

        ↓

```

というところまで切り分けた。

# 4. 以前採用した対策

そこで、

``` python
keyboard.add_hotkey()
```

による組み合わせ判定を使用しないことにした。

代わりに、

``` python
keyboard.on_press()
```

で個々のキーイベントを取得し、

``` python
keyboard.is_pressed()
```

でCtrlとShiftの状態を確認した。

代表的な処理は次のようなものだった。

``` python
def on_key_press(event):
    if event.name != "space":
        return

    if not keyboard.is_pressed("ctrl"):
        return

    if not keyboard.is_pressed("shift"):
        return

    show_window()


def hotkey_worker():
    keyboard.on_press(on_key_press)
    keyboard.wait()
```

考え方は、

``` text
何かキーが押された
        ↓
on_key_press(event)
        ↓
Spaceか？
        ↓ YES
Ctrlが押されているか？
        ↓ YES
Shiftが押されているか？
        ↓ YES
show_window()
```

というものだった。

この変更後は動作が改善したため、

> しばらく実運用して様子を見る

という結論にしていた。

# 12. ただし、以前の対策と今回の対策には違いがある

ここは重要である。

以前の対策は、

``` python
keyboard.on_press()
```

と、

``` python
keyboard.is_pressed()
```

を組み合わせていた。

つまり、

``` text
keyboard.on_press()
        ↓
Spaceの押下イベント
        ↓
is_pressed("ctrl")
is_pressed("shift")
        ↓
show_window()
```

という**イベント駆動方式を一部残した構成**だった。

一方、今回試している方式は、

``` python
while True:
    ctrl = keyboard.is_pressed("ctrl")
    shift = keyboard.is_pressed("shift")
    space = keyboard.is_pressed("space")

    ...
```

という方式である。

つまり、

``` text
while True
        ↓
is_pressed("ctrl")
is_pressed("shift")
is_pressed("space")
        ↓
自前で3キー成立判定
        ↓
show_window()
```

となる。

今回は、

``` python
keyboard.add_hotkey()
```

だけでなく、

``` python
keyboard.on_press()
```

にもホットキー成立の入口を依存しない。

# 14. 今回のポーリング方式

現在試している処理は次のようなものになる。

``` python
def hotkey_worker() -> None:
    hotkey_pressed = False

    while True:
        ctrl = keyboard.is_pressed("ctrl")
        shift = keyboard.is_pressed("shift")
        space = keyboard.is_pressed("space")

        if ctrl and shift and space:
            if not hotkey_pressed:
                hotkey_pressed = True
                show_window()
        else:
            hotkey_pressed = False

        time.sleep(0.05)
```

この方式へ変更後、現時点では従来より長く
ホットキーが反応し続けており、動作は良好である。

ただし、まだ長期運用確認中である。

# 15. `hotkey_pressed` の役割

ポーリングでは、キーを押している間、

``` text
50ms
50ms
50ms
50ms
...
```

と何度も同じ状態を検出する。

単純に、

``` python
if ctrl and shift and space:
    show_window()
```

としてしまうと、1回の操作で `show_window()`
が何度も呼ばれる可能性がある。

そこで、

``` python
hotkey_pressed
```

という状態変数を使用する。

``` text
最初
hotkey_pressed = False

        ↓

3キー成立

        ↓

Falseなのでshow_window()

        ↓

hotkey_pressed = True

        ↓

まだ押している

        ↓

Trueなので何もしない

        ↓

キーを離す

        ↓

hotkey_pressed = False

        ↓

次回の入力を受付可能
```

この処理によって、

> 「現在押されている」という状態から「1回押した」というイベントを自前で作る

ことができる。

# 19. 技術資料は「その時点の判断」を残す

不具合調査では、後から新しい事実が分かることがある。

そのため資料には、

``` text

```

と早い段階で断定するより、

``` text
今回の観測では○○だった

そのため△△を原因候補として絞り込んだ

現在は実運用で確認中
```

と書く方が正確である。

こうしておけば、後から結果が変わっても資料同士が矛盾しにくい。

# 21. 今回の考察から学べるデバッグの考え方

今回の事例には、ホットキー以外にも使える重要な考え方が含まれている。

## 21.1 一度直ったように見えても調査は終わりとは限らない

``` text
修正
 ↓
改善
```

したからといって、原因を完全に理解したとは限らない。

長時間の実運用によって初めて分かる問題もある。

------------------------------------------------------------------------

## 21.2 過去の判断を無理に否定しない

以前の対策は、

``` text
その時点では改善した
```

という事実がある。

後からより良い方法が見つかったからといって、
以前の判断が無意味になるわけではない。

------------------------------------------------------------------------

## 21.3 実運用もデバッグの一部

短時間の動作確認だけでは再現しない問題がある。

今回も、

``` text
短時間
    → 正常

長時間使用
    → 問題発生
```

という性質があった。

したがって、

> 実際に使いながら様子を見る

こと自体が重要な検証になる。

------------------------------------------------------------------------

## 21.4 高機能なAPIより単純な処理が有利な場合もある

`keyboard.add_hotkey()` は便利である。

しかし今回の用途は、

``` text
Ctrl + Shift + Space
```

という1種類のホットキーを監視するだけである。

そのため、

``` python
keyboard.is_pressed()
```

を3回使って自分で判定しても、コードは十分単純である。

内部動作が見えやすく、問題発生時にも調査しやすい。

------------------------------------------------------------------------

## 21.5 「イベント」と「状態」は別の考え方

以前は、

``` text
キーが押された
```

というイベントを入口にしていた。

今回は、

``` text
今、このキーが押されているか
```

という状態を定期的に確認している。

つまり、

``` text
イベント駆動
```

から、

``` text
状態監視（ポーリング）
```

へ考え方を変えた。

この違いは、PLC監視やネットワーク通信などでもよく登場する。

------------------------------------------------------------------------

# 22. PLC監視との共通点

今回のポーリング方式は、PLC監視の考え方にも似ている。

例えば、

``` text
50msごとに

B10.0はON？
B10.1はON？
B10.2はON？
```

と確認する処理と、

``` text
50msごとに

CtrlはON？
ShiftはON？
SpaceはON？
```

と確認する処理は、基本的な考え方が同じである。

さらに、

``` python
hotkey_pressed
```

は、同じ状態を何度も処理しないためのラッチのような役割を持つ。

``` text
条件OFF
    ↓
条件ON
    ↓
1回だけ処理
    ↓
ON中は再処理しない
    ↓
条件OFF
    ↓
次のONを受付
```

という考え方は、設備監視でも非常に汎用性が高い。

------------------------------------------------------------------------

# 23. 現時点での結論

以前の資料と今回の調査結果は、基本的には矛盾していない。

むしろ今回の追加調査によって、

``` text
keyboard全体が停止しているわけではない

is_pressed()は問題発生後も動いている

3キー同時押しも自前なら判定できる

add_hotkey()経由のコールバックだけ発火しない
```

ということが、以前より明確になった。

一方、対策方法は、

``` text
以前
on_press() + is_pressed()

今回
is_pressed()のみのポーリング
```

へさらに単純化された。

現時点ではポーリング方式の方が長く安定して動作している。

ただし、

> 完全に解決した

と断定する段階ではなく、

> 現時点では良好なので、この方式で実運用を続けて確認する

という位置づけが適切である。

------------------------------------------------------------------------

# 24. 最終まとめ

今回の一連の調査は、

``` text
不具合発生
    ↓
原因候補を分解
    ↓
ログで境界を確認
    ↓
最小限の対策
    ↓
実運用
    ↓
再発
    ↓
さらに細かく調査
    ↓
より単純な対策
    ↓
再び実運用
```

という流れになった。

重要なのは、以前の資料と今回の資料のどちらか一方が
「正解」で、もう一方が「間違い」ということではない。

それぞれ、

> **その時点で観測できた事実と、その事実に基づいて行った判断**

を記録している。

このように履歴を残しておくことで、将来また問題が発生した場合にも、

``` text
以前どこまで調べたのか
何を確認したのか
何をまだ確認していないのか
どの対策でどの程度改善したのか
```

をすぐに把握できる。

今回のText Input Helperの事例は、 単なるホットキー不具合の記録ではなく、

> **不具合を一度で決めつけず、観測 → 仮説 → 対策 → 実運用 →
> 再評価を繰り返す**

という、実践的なデバッグ方法の学習例として残しておく価値がある。
